# 熙心健康体检管理系统后端设计

## 背景与约束

本设计依据 `文档/第04组-需求规约-熙心健康体检管理系统_修改版.docx` 与 `文档/08.第04组-项目功能结构表-熙心健康管理系统.xlsx` 制定。需求规约要求系统采用前后端分离 B/S 架构，后端使用 Java、Spring Boot/Spring Cloud、MySQL、Redis、RESTful API、JWT、RBAC、审计日志，并以 `/api/v1` 做接口版本管理。

用户已选择首版采用 Spring Boot 模块化单体，而不是直接创建多服务 Spring Cloud 工程。该选择保留业务域边界，降低课程设计阶段的启动、联调和部署复杂度，后续可按包边界拆分为微服务。

## 目标

创建一个可启动、可测试、可演示的后端工程，覆盖需求文档和功能结构表中的核心必选模块：认证安全、健康档案、预约、订单支付状态、体检流程、检查结果录入与审核、报告管理、异常分析、基础配置、RBAC、账号管理、操作日志、消息通知基础能力。

## 技术栈

- Java 17。
- Spring Boot 3。
- Spring Security + JWT，用于登录认证、Token 刷新和接口鉴权。
- MyBatis-Plus，用于实体映射、分页和基础 CRUD。
- MySQL 8，使用 UTF-8MB4 和 InnoDB。
- Redis，用于 Refresh Token、登录状态、限流计数和热点配置缓存。
- Flyway，用于数据库迁移。
- springdoc-openapi，用于接口文档。
- JUnit 5、Spring Boot Test、Testcontainers 或 H2 测试配置，用于关键业务测试。
- Docker Compose，提供 MySQL、Redis 和后端本地启动环境。

## 架构

项目采用模块化单体，包结构按业务域划分：

- `auth`：注册、登录、Token 刷新、密码修改、账号注销、当前用户信息。
- `iam`：RBAC 角色、权限、账号管理、数据权限基础模型。
- `profile`：个人健康档案、家属档案、既往病史、过敏史、紧急联系人。
- `config`：体检项目、套餐、分院、科室、业务规则、报告模板基础配置。
- `appointment`：套餐浏览、分院时段查询、预约创建、取消、改期。
- `order`：订单创建、支付模拟发起、支付回调模拟、退款申请记录。
- `exam`：前台签到、指引单、科室队列、体检进度跟踪。
- `result`：检查结果录入、参考范围比对、异常标记、结果审核、批量审核。
- `report`：报告生成记录、报告查询、下载链接、历史报告关联。
- `analysis`：异常指标检测、历年趋势数据、高危人群识别基础记录。
- `notification`：预约确认、体检提醒、报告完成、异常预警的站内消息记录。
- `audit`：关键操作审计日志，记录操作人、对象、结果、IP、User-Agent、TraceID。
- `common`：统一响应、异常处理、分页、枚举、加密、时间、当前用户上下文。

各业务域只通过 Service 接口协作，避免 Controller 直接跨域访问 Mapper。数据库表按业务域使用统一前缀和审计字段，核心表软删除。

## 数据设计

首版数据库迁移脚本创建以下核心表：

- 用户权限：`sys_user`、`sys_role`、`sys_permission`、`sys_user_role`、`sys_role_permission`。
- 健康档案：`t_health_profile`、`t_family_member`。
- 基础配置：`t_branch`、`t_department`、`t_exam_item`、`t_exam_package`、`t_exam_package_item`、`t_business_rule`、`t_report_template`。
- 预约订单：`t_appointment`、`t_order`、`t_payment_record`、`t_refund_record`。
- 体检流程：`t_exam_record`、`t_guide_sheet`、`t_department_queue`、`t_exam_progress`。
- 结果报告：`t_check_result`、`t_result_review`、`t_exam_report`、`t_report_history_link`。
- 分析健康管理：`t_health_analysis`、`t_health_management`。
- 通知审计：`t_notification`、`t_operation_log`。

敏感字段包括手机号、身份证号、紧急联系人电话等，首版提供字段加密工具和实体层加解密点；密码必须使用 BCrypt 存储。报告文件、头像、PDF 等文件类能力首版只保存 URL/对象键，不直接实现真实对象存储。

## 接口设计

所有接口以 `/api/v1` 开头。公开接口仅限注册、登录、刷新 Token 和公开套餐查询。其他接口默认需要 `Authorization: Bearer <JWT>`。

首版提供以下接口分组：

- `/api/v1/auth/**`：注册、登录、刷新 Token、登出、修改密码。
- `/api/v1/profiles/**`：本人档案、家属档案维护。
- `/api/v1/packages/**`、`/api/v1/branches/**`：套餐、分院、科室、时段查询。
- `/api/v1/appointments/**`：创建预约、取消预约、修改预约时间、查询预约。
- `/api/v1/orders/**`：订单查询、支付模拟、退款申请。
- `/api/v1/exams/**`：签到、体检记录、指引单、队列、进度。
- `/api/v1/results/**`：结果录入、异常判定、审核、批量审核。
- `/api/v1/reports/**`：报告生成记录、报告查询、报告下载链接。
- `/api/v1/analysis/**`：异常指标、趋势数据、高危识别记录。
- `/api/v1/admin/**`：基础配置、账号、角色、权限、审计日志、统计。
- `/api/v1/notifications/**`：通知列表、已读状态。

## 业务规则

- 新注册用户默认赋予普通用户角色。
- 普通用户只能访问本人及授权家属数据。
- 医生只能录入或查看分配科室/体检流程相关数据。
- 审核医生负责结果审核、报告确认和异常报告处理。
- 运营管理员可管理套餐、分院、规则和统计，但不能查看个人健康明细。
- 系统管理员负责账号、角色、权限和审计日志查询。
- 只有预约状态允许且未超过规则限制时，才能取消或改期。
- 只有支付成功或线下确认后的预约才能进入到检签到流程。
- 检查结果录入后根据参考范围和危急值阈值自动标记正常、异常或危急值。
- 报告必须在检查结果审核通过后生成和发布。
- 报告审核、危急值处理、权限变更、数据导出等关键操作必须写入审计日志。

## 外部依赖处理

首版不对接真实支付、短信、HIS、LIS、PACS、MinIO 或 AI 服务。对应能力使用接口适配层：

- 支付适配器：提供模拟支付和模拟回调，保留真实微信/支付宝实现入口。
- 通知适配器：写入站内消息，保留短信、微信模板消息实现入口。
- 医疗系统适配器：保留 HIS/LIS/PACS 导入接口，首版使用本地录入。
- 文件存储适配器：保留对象存储接口，首版只保存逻辑文件 URL。
- AI 解读适配器：不做医学结论生成，只保留可替换的接口预留。

## 错误处理与审计

使用统一响应结构和全局异常处理。参数校验错误、认证失败、权限不足、业务状态冲突、资源不存在、系统错误分别返回明确错误码。关键业务状态变更使用审计注解或显式审计服务记录日志。

## 测试策略

首版测试覆盖以下路径：

- 注册、登录、刷新 Token、密码加密和鉴权失败。
- RBAC 权限拦截和普通用户越权访问。
- 预约创建、号源扣减、取消、改期的状态约束。
- 支付模拟后订单和预约状态联动。
- 签到生成体检记录与进度。
- 检查结果自动异常判定。
- 审核通过后报告可生成，未审核不得生成。
- 关键操作写入审计日志。

## 不在首版范围

- 真实第三方支付资金清结算。
- 真实短信、微信小程序、支付宝小程序推送。
- HIS/LIS/PACS 真实接口映射。
- 真实 PDF 报告渲染和电子签章。
- Elasticsearch 全文检索。
- Kafka/RabbitMQ 异步化。
- Kubernetes 生产部署。
- AI 医学解读和跨机构互通。

这些能力只保留清晰接口和模拟实现，避免影响课程设计首版可运行性。

## 验收标准

- 本地可通过 Docker Compose 启动 MySQL、Redis 和后端。
- 后端启动后可访问 OpenAPI 文档。
- Flyway 可初始化数据库结构和基础角色权限种子数据。
- 认证、预约、订单、体检流程、结果审核、报告、配置、权限、日志主干接口可调用。
- 关键测试通过。
- 代码结构清晰，业务域边界可作为未来微服务拆分依据。
